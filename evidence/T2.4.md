# T2.4 — Run Python 2.7 and client bytecode on Windows

Status: **done — the vendored 2.7.18 runtime is wired into the Windows build and `metin2client.exe` boots the interpreter.**

- agent: agent-06 (DeepSeek V4.1 Flash)
- date: 2026-10-31
- command: `scripts/fetch-windows-python.sh` + `cmake --preset windows` + Wine probe
- before: the Windows configure stopped at `PYTHON_LIBRARIES` (NOTFOUND); there was no Windows Python runtime or import lib in the tree or image.
- after: the official PSF 2.7.18 **amd64** distribution is vendored into `/opt/openmt2/win64`, the configure resolves `PYTHON_INCLUDE_DIR=/opt/openmt2/win64/include/python2.7` and `PYTHON_LIBRARY=/opt/openmt2/win64/lib/libpython27.a`, and a cross-built `Py_Initialize` probe runs under Wine printing `py27 2.7.18`.
- notes:
  - **Source:** `python-2.7.18.amd64.msi` from python.org, sha256 `b74a3afa1e0bf2a6fc566a7b70d15c9bfabba3756fb077797d16fffa27800c05`; extracted with `msitools` (added to the image).
  - **Layout:** `bin/python27.dll`, `bin/msvcr90.dll`, `python/Lib`, `python/DLLs`, `include/python2.7/`, `lib/libpython27.a`.
  - **Import lib:** the MSI only ships the MSVC `python27.lib`; `scripts/fetch-windows-python.sh` parses the DLL exports with `objdump` (12 198 symbols) and generates a MinGW import lib with `dlltool`.
  - **Wiring:** the existing package CMake already falls back to `find_library(NAMES python2.7 python27 …)` / `find_path(NAMES python2.7/Python.h …)`, and the T2.3 toolchain puts the prefix in `CMAKE_FIND_ROOT_PATH`, so no package change was needed. The configure now reaches `Generating done`.
  - **Dist:** `build-windows.sh` copies `python27.dll` and `msvcr90.dll` into `dist/`; the `Lib`/`DLLs` layout for the shipped tree is T3.1's concern (the client sets `Py_SetPythonHome` only on Linux today).
  - **Probe evidence:** `probe.c` includes `Python.h`, links `-lpython27` against the generated import lib, and under `wine64` prints `py27 2.7.18` (Wine in the image is 32-bit only, so `wine64` was installed for the probe; the image needs `wine64` before T3.2's Windows smoke test).
  - **Boot check (final):** the T1.9 landing links `metin2client.exe`; run from `dist/` under Xvfb + Wine with the packed `dist/pack/*.zip` and the `lib/*.pyc` set. The process **stays alive for 35 s** (window mapped), `syserr.txt` contains no `RunMain Error`/`Failed to initialize Python Launcher`, and `objdump -p` shows `python27.dll` as the first import. That is the `system.py` boot path: it is only reached after `CPythonLauncher::Create()` and the `lib/` filename check pass.
  - The task sheet's literal `wine dist/metin2client.exe --version` cannot be used: the client has no `--version` handler (it only knows `/timestamp`, `--force-set-locale`, …). The boot smoke above is the substituted verification; a `--version`/`/timestamp` flag would be a small follow-up.
  - **Image prerequisites:** `wine64` and `xauth` are now installed by the Dockerfile (the image previously had 32-bit Wine only, and `xvfb-run` needs `xauth`).
  - **Follow-ups (not T2.4):** the client sets `Py_SetPythonHome` only on Linux; the shipped `Lib`/`DLLs` layout for the Windows tree, the missing `libstdc++-6.dll`/`libgcc_s_seh-1.dll` runtime DLLs and the pack-archive assembly are T3.1.
